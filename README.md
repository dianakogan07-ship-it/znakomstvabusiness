# B2B-сервис деловых знакомств для бизнес-форума

Tinder-подобный сервис для нетворкинга компаний на деловом форуме:
компании свайпают карточки друг друга, взаимный интерес превращается
в мэтч и открывает встроенный чат. Полностью статический фронтенд
(HTML/CSS/JS без сборки) на GitHub Pages + Supabase (Postgres) как БД
и «бэкенд» в виде SQL-функций — без отдельного сервера.

## Как устроена аутентификация (и почему именно так)

В ТЗ было два варианта: Supabase Auth с синтетическими email, либо
своя таблица + хеш пароля + Edge Function. Здесь реализован третий,
более простой путь на основе идеи №2:

- **Компании и админ** хранятся не в Supabase Auth, а в обычной
  таблице `companies` (+ отдельный пароль администратора). У этого
  есть жёсткая причина: по ТЗ администратор должен уметь **посмотреть
  и скопировать пароль компании повторно**, в любой момент. Supabase
  Auth (как и любая нормальная аутентификация) хранит только
  необратимый хеш и никогда не отдаёт пароль обратно — с ним это
  требование просто нереализуемо. Поэтому пароли компаний хранятся в
  БД в **симметрично зашифрованном** виде (не в открытом тексте, но
  и не в виде одностороннего хеша) и расшифровываются только внутри
  серверной функции по запросу администратора.
- Вместо Edge Function проверка логина/пароля и вся бизнес-логика
  (лента, свайпы, мэтчи, чат, CRUD компаний) реализована как обычные
  **Postgres-функции** (`SECURITY DEFINER`), вызываемые из фронтенда
  через `supabase.rpc(...)`. Результат тот же самый — код выполняется
  на сервере Supabase, а не в браузере, — но не нужно ничего
  разворачивать через Supabase CLI: весь «бэкенд» это один SQL-файл
  (`supabase/schema.sql`), который один раз выполняется в SQL Editor.
  Для организатора форума без своей инфраструктуры это ощутимо проще
  в установке и поддержке, чем Edge Functions.
- Таблицы закрыты от прямого доступа через REST/anon-ключ (RLS
  включён, ни одной разрешающей политики нет, все грант-права
  отозваны). Единственный способ что-то прочитать/записать —
  вызвать одну из функций из `schema.sql`, а они сами решают, что
  можно текущему вызывающему (проверяя токен сессии), а что нет.
- При логине компания получает случайный токен сессии
  (`company_sessions`), админ — отдельный админ-токен
  (`admin_sessions`). Токен хранится в `localStorage` браузера и
  передаётся первым параметром во все защищённые функции — сервер
  сам вычисляет, кто вызывает функцию, идентификатор компании из
  браузера никогда не используется напрямую.

**Известное ограничение.** Поскольку вход компаний идёт через
`anon`-ключ (единственно доступный фронтенду), а не через
Supabase Auth, теоретически человек, нашедший URL и anon key вашего
проекта (они видны в коде фронтенда — это нормально для статических
сайтов), может напрямую вызвать RPC-функции. Практически это ничего
ему не даёт: без пароля конкретной компании он не сможет ни войти,
ни прочитать список компаний с паролями (это доступно только через
`admin_login`), ни отправить сообщение вне мэтча. Для закрытого
мероприятия на 50–100 известных участников этого достаточно; для
публичного интернет-сервиса такую схему усиливать. Понадобилось бы
дополнительно (rate-limiting на логин, капча и т.п.).

## Структура проекта

```
index.html          — вход для компании (логин/пароль)
app.html             — кабинet компании: Лента / Приглашения / Диалоги
admin.html           — вход и панель администратора
css/style.css        — общий дизайн (тёмно-синий/чёрный + белый, синие акценты)
js/config.js         — URL и anon key вашего Supabase-проекта (заполнить)
js/supabase-client.js— инициализация supabase-js + обёртка над rpc()
js/auth.js           — логика логина компании
js/app.js            — логика кабинета компании
js/admin.js          — логика админ-панели
js/swipe.js          — механика свайпа карточек (мышь + тач)
js/utils.js          — вспомогательные функции (тосты, копирование и т.п.)
supabase/schema.sql  — вся схема БД + бизнес-логика на стороне Supabase
```

## Установка — шаг за шагом

### 1. Создайте проект в Supabase

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) и создайте
   новый проект (бесплатного тарифа хватает с большим запасом на
   50–100 компаний).
2. Дождитесь, пока проект поднимется (обычно 1–2 минуты).

### 2. Выполните схему БД

1. В панели проекта откройте **SQL Editor → New query**.
2. Откройте файл `supabase/schema.sql` из этого репозитория, скопируйте
   всё содержимое.
3. **Перед запуском** замените в тексте два значения на свои:
   - `_enc_key()` — придумайте длинную случайную строку (это ключ
     шифрования паролей компаний, например 32+ случайных символа).
   - `_admin_password()` — пароль, под которым вы будете заходить в
     `/admin`.
   Меняйте эти значения **только в SQL Editor**, не в файле в git —
   в публичном репозитории должны остаться только плейсхолдеры
   `CHANGE_ME_...`.
4. Нажмите **Run**. Должно выполниться без ошибок — появятся все
   таблицы и функции.

Если позже захотите сменить пароль администратора — откройте SQL
Editor и выполните заново только блок `create or replace function
_admin_password()` с новым значением.

### 3. Получите URL и anon key

1. В панели проекта откройте **Settings → API**.
2. Скопируйте **Project URL** и **anon public key** (не `service_role` —
   его использовать во фронтенде нельзя ни в коем случае).
3. Откройте `js/config.js` в этом репозитории и вставьте оба значения:

```js
export const SUPABASE_URL = 'https://xxxxxxxx.supabase.co';
export const SUPABASE_ANON_KEY = 'eyJhbGciOi...';
```

anon key публичен по своей природе (он и так виден в коде любого
статического сайта) — его наличие в открытом репозитории безопасно
именно потому, что вся логика доступа реализована через RLS +
RPC-функции на шаге 2, а не через прямые права на таблицы.

### 4. Проверьте локально (необязательно)

Файлы используют ES-модули, поэтому открыть `index.html` двойным
кликом (`file://`) не получится — браузер заблокирует импорты. Запустите
любой локальный статический сервер из корня проекта, например:

```bash
python3 -m http.server 8000
```

и откройте `http://localhost:8000`.

### 5. Задеплойте на GitHub Pages

1. Запушьте этот репозиторий на GitHub (уже сделано, если вы читаете
   этот файл из репозитория).
2. В репозитории откройте **Settings → Pages**.
3. В разделе **Build and deployment** выберите **Deploy from a branch**,
   ветка — `main`, папка — `/ (root)`. Сохраните.
4. Через минуту-две сайт появится по адресу вида
   `https://<ваш-логин>.github.io/<репозиторий>/`.
5. Админ-панель — `.../admin.html`, вход для компаний — корень сайта
   (`index.html`).

Сборка не нужна — весь сайт уже статический HTML/CSS/JS.

### 6. Добавьте компании

1. Зайдите на `.../admin.html`, введите пароль администратора (из
   шага 2).
2. **+ Добавить компанию** → заполните карточку (название, фото по
   ссылке, сфера деятельности, «чем занимается», «что предлагает»,
   «что интересно обсудить», имя контактного лица) и логин/пароль
   (вручную или кнопкой «Сгенерировать»).
3. После сохранения сверху появится панель с логином и паролем и
   кнопками «скопировать» — передайте их участнику любым удобным
   способом (лично, почтой и т.п.).
4. В любой момент логин и пароль компании можно посмотреть повторно
   в общей таблице — в столбце «Доступ» (иконка 👁 показывает пароль,
   ⧉ копирует).

## Модель данных

- `companies` — карточка компании + логин + зашифрованный пароль.
- `swipes` — решения (`left`/`right`) кто кого свайпнул.
- `messages` — сообщения внутри мэтча (без email/телефонов — общение
  только внутри сайта).
- `company_sessions` / `admin_sessions` — токены активных сессий.
- Мэтч не материализуется отдельной таблицей, а вычисляется на лету
  (взаимные `swipes` с `direction = 'right'`) — при таком масштабе
  (50–100 компаний) это дешевле, чем поддерживать синхронизацию
  отдельной таблицы.

Подробности бизнес-логики — в комментариях `supabase/schema.sql`.

## Дизайн

Тёмно-синий/чёрный фон, белый текст, синие акценты — CSS-переменные
в `css/style.css` (`--bg`, `--accent` и т.п.), мобильно-адаптивная
вёрстка, свайп карточек через Pointer Events (единый код для мыши и
тач-жестов).
